# Verification, validation and release evidence

This is the current evidence strategy for the LIS described in the [product scope](../project-scope.md#product-decision). Synthetic development is authorized; clinical use, signing, deployments and external services require separate approvals ([implementation plan](../planning/implementation-plan.md#scope)). The scenario tables define expected evidence, not a record that every scenario passed. Current gaps are in [open gate items](open-items-g1-g2.md) and [pending scope decisions](scope-decisions.md).

## Separate the questions

Software verification asks whether the implementation satisfies its specified behavior. Laboratory validation asks whether the configured system is suitable for the lab's intended use, methods, staff and interfaces. Operational qualification asks whether the deployed environment can protect data, run reliably, recover, and be supported. All three matter; a passing CI run establishes only the behavior actually tested in that environment.

Quality and laboratory owners define the required protocol and approve the intended-use assessment. IQ/OQ/PQ terminology can be adopted if it fits the laboratory quality system, but this document does not assert it is a universal statutory format for every LIS. Changes require a risk-based impact assessment and appropriate revalidation.

On one host computer each software update is also a laboratory acceptance event: the lab, not the project, decides that a new or revised LIS version performs acceptably before routine use. The project supplies the evidence in a [release validation package](#release-validation-package-for-laboratory-acceptance); any hosted cloud service needs its own operational evidence (GC-1, GC-2).

FDA's Computer Software Assurance guidance (final 2026-02-03, SR-080; see [regulatory landscape §9](../research/regulatory-landscape.md#9-fda-electronic-signatures-and-clinical-functionality)) addresses device manufacturers' production and quality-system software and does not bind a clinical laboratory's LIS. The project may use it as an **optional** risk-based model: identify each feature's intended use, judge whether a failure poses high process risk, and choose proportionate assurance (scripted testing for high-risk functions, unscripted testing where justified, a record sized to the risk). It does not replace laboratory validation, CLIA obligations or the scenario evidence below.

## Traceability model

For each applicable functional, regulatory and nonfunctional requirement, maintain: requirement ID and version → hazard/control → design/ADR or SOP → scenario and expected outcome → release/configuration/instrument versions → executed evidence → discrepancy resolution → named reviewer and acceptance date. Initial ledgers use REQ, REG, NFR, RISK, WF, INV and VAL identifiers. A requirement is not covered merely because it appears in a table.

The scenario set below seeds detailed protocols. It is not complete requirement-level coverage. Before an operational pilot, expand it so every applicable P0 functional requirement, REG row and accepted NFR has evidence or a justified, accepted not-applicable disposition. Research gaps cannot be closed by marking a test “not run.”

### Test layers

Use focused domain tests for state invariants and numerical semantics; property/boundary tests where input spaces matter; integration tests on the production engine of each side for constraints, transactions and outbox behavior; contract tests against versioned partner fixtures; end-to-end UI tests for the critical human workflows in each supported web engine (WebView2, WKWebView, WebKitGTK); and load, security, accessibility and restore exercises for relevant nonfunctional claims. Use independent expected results for cutoff, units, report contents and amendments.

Test the local LIS on SQLite with its production settings (STRICT, WAL, `synchronous=FULL`, one writer, `BEGIN IMMEDIATE`). Any separately authorized external service needs evidence for its own selected database and operating environment. Failure injection includes physical and virtual-machine power-off, termination between transaction commit and dispatch, and network loss. Installer, update, sign-in-screen listening, keep-awake, serial and printing qualification runs on real hosts of each supported OS in the [OS test matrix](../governance/engineering-standards.md#os-test-matrix). The release-versus-invalidation tests in both transaction commit orders (VAL-06) still apply with a single writer.

Security testing includes restricted file handling, malformed payloads, auth/session controls, privilege escalation and data egress/log inspection. Automated scanning complements human threat review. Test both migration forward paths and the realistic recovery strategy; reverting software cannot unsend a report or remove a partner's accepted message.

Fixtures should cover collection/receipt/timezone differences, multiple containers and aliquots, failed validity/QC, direct definitive and reflex orders, repeats/dilutions, cutoffs and censoring, result corrections, referral attribution, consent/provenance, duplicate identities and message collisions. For drug monitoring they should also cover per-patient order evidence with and without signatures or diagnoses, practice profiles and expired standing orders, client point-of-care results, mapped, unmapped and stale medication lists, upstream re-export sequences, same-day accessions with class mappings, payer records requests and patient access requests. Retain fixture author, intended behavior, source/method assumptions and license rights. A public synthetic dataset is not evidence of instrument analytical performance.

## Release validation package for laboratory acceptance

CMS surveyor guidance asks how a laboratory determines that "a new or revised LIS program" performs acceptably before routine use, and expects LIS calculations to be verified before patient results ([regulatory landscape §15.4](../research/regulatory-landscape.md#154-clia-with-one-pc-as-the-laboratorys-record-system)). Each release should supply the evidence a laboratory needs to accept it (REQ-OPS-006, NFR-24, REG-047, Q-34). This is a proposal; the package contents and risk classes need quality-lead approval.

| Package element | Content |
| --- | --- |
| Identity and integrity | Version; hashes and signatures of each OS package (Windows MSI or NSIS, macOS app or .dmg, Linux AppImage, .deb, .rpm), the Minisign update signatures and the update manifest; SBOM and build provenance (NFR-21); Tauri, Rust toolchain, SQLite, Typst renderer and any bundled native-library or auxiliary-tool versions; web engine versions tested per OS; support end date |
| Change summary in laboratory terms | Changed workflows, screens, calculations, report and label templates, interface mappings and defaults, each traced to requirement and risk IDs |
| Risk class (proposed) | **Class 1:** security or runtime patch with no functional change. **Class 2:** functional change outside clinical computation, release logic, report content and interface mapping. **Class 3:** change to clinical computation, release or QC gates, report content, interface mapping or a data migration |
| Project verification evidence | Executed VAL protocols on each OS of the reference [OS test matrix](../governance/engineering-standards.md#os-test-matrix), reported per OS, with results, deviations and resolutions; the NFR-33 parity checks (VAL-57); regression of the case pack, including calculation and decimal checks; upgrade and rollback rehearsal from each supported prior version |
| Migration and rollback | Schema and data changes, expected duration, snapshot size, rollback steps and their limits (work after the upgrade must be reconciled) |
| Laboratory acceptance protocol | Checks the lab runs, scaled to the risk class, on a staging copy restored from a snapshot or on the host after approval: the synthetic case pack, spot-checks of calculations against the lab's own configured units and cutoffs, a report and label compared with approved examples, a test message per enabled interface. Class 1 needs a short smoke check. The lab runs the checks on its own OS; the same short UI smoke check follows OS or web-engine updates outside our releases |
| Acceptance record template | Version and hash, risk class, checks run and outcomes, deviations, decision, and signature of the laboratory director or designee with date |
| Known issues | Open defects, unsupported configurations, workarounds |

The project's evidence shows what was verified on the reference configuration. It does not establish suitability for a lab's configured intended use; only the lab's signed acceptance does. Qualified personnel may assist with planning and executing the lab's checks, but the director or designee signs ([§15.9](../research/regulatory-landscape.md#159-open-source-distribution-and-validation)). An expedited security release uses the same package with a Class 1 scope; it is never installed without the recorded approval.

## Change and evidence control

For an executed protocol record the purpose, preconditions, input provenance, expected results, exact configuration, person executing it, timestamps, observed outputs, deviations, resolution and approval. Secure sensitive validation evidence in the laboratory's authorized system, or the service provider's for cloud-service evidence; the repository retains reusable protocols, current limitations and source provenance. Development-session records stay out of tracked documentation ([AGENTS.md](../../AGENTS.md)); release qualification evidence is retained in the accountable release or laboratory evidence system, with integrity and retrieval controls. Release notes must name changed workflows, mappings, migration effects and revalidation scope, in the [release validation package](#release-validation-package-for-laboratory-acceptance). Signed binaries or commit signatures establish provenance of a software artifact, not clinical correctness.

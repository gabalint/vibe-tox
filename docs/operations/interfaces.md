# Interfaces

Status: **implemented on synthetic data; fifth delivery step: interface contracts and acceptance tests**. The Interfaces menu receives HL7 orders from a clinic's EMR and sends HL7 results, issued report PDFs and billing handoff files to outside systems, through a folder or the partner's SFTP server, and HL7 over MLLP with a partner on the lab network: results sent, orders received (REQ-INT-001–004, REQ-INT-006, REQ-ORD-001, REQ-RPT-003, REQ-RPT-011–013, REQ-BIL-002). The built-in help, Interfaces topic, describes every field and action; this guide covers setup, behavior and recovery. Analyzers are configured separately, under Laboratory setup › Instruments.

## What is available

| Message type | Made when | Direction | Protocol | Default file name |
| --- | --- | --- | --- | --- |
| HL7 Results (ORU^R01, v2.5.1) | A report revision is released; a withdrawal message when the report is withdrawn | Out | Folder, the partner's SFTP server, or MLLP – LIS connects | `{accession}_r{revision}_{date}.hl7` (none over MLLP) |
| Report PDF | A report revision is released; its withdrawal notice when the report is withdrawn | Out | Folder, or the partner's SFTP server | `{accession}_r{revision}_{date}.pdf` |
| Billing JSON (`bil-handoff-v2`) | A billing handoff is created | Out | Folder, or the partner's SFTP server | `billing-{handoff}_{date}.json` |

In a report's file name, `{accession}` is the report number (the accession number and the specimen type code, so two specimens of one accession never share a name) and `{revision}` the revision number; a withdrawal's revision reads `<n>-withdrawn`.

| HL7 Orders (OML^O21, or ORM^O01, v2.5.1) | The clinic's EMR writes a file, or sends a message | In | Folder, the clinic's SFTP server, or MLLP – LIS listens | — (read, not named) |

A folder is on this computer or on the lab network. Every connection has an [interface contract and acceptance tests](#interface-contracts-and-acceptance-tests) before patient data goes or comes. HL7 acknowledgement files are not available, back to the clinic or from a partner, and no setting enables them: a file connection's outcome stays **Outcome unknown**.

## HL7 Orders (incoming)

An HL7 Orders connection reads the order messages a clinic's EMR leaves in an input folder, local or on the clinic's SFTP server, every *Check every* seconds (10–3600) while the app is open, at the sign-in screen too; or it listens for the EMR to send them over MLLP ([below](#mllp--lis-listens)). Its partner is one of the laboratory's clients: every order it receives is for that client. It reads or listens only once started with a destination check that covers its input folder, server or listener and an approved interface contract whose acceptance tests passed, and never while a recovery reconciliation is open.

- **Reading.** Only complete files are read: `*.hl7` (any case), not hidden, never `*.tmp`; at most 20 per reading. The bytes are stored first; then one transaction records what the message became, with the order it made; then the file moves to Processed or Failed › year › month (such as `Processed/2026/11/clinicA_000124.hl7`), never replacing a file. A file read again after a crash before its move is only moved.
- **Reading problems.** A folder that is missing or not reachable, an SFTP server that does not answer or refuses the sign-in, or a file that cannot be read, saved in the LIS or moved puts a started connection in status **Error**. Overview's **Last connection** shows the reading's time and its first problem, and a file not read stays in the input folder for the next reading. The connection is **Active** again after the first reading that works. The latest reading is kept while the app runs; after a start the first reading shows it again. A message the LIS refuses is the clinic's content, not a connection problem: it shows under **Logs › Rejected** and the connection stays Active.
- **Reader.** The LIS's own narrow reader ([ADR 0007](../architecture/decisions/0007-integration-edge-and-interface-engines.md) §7) reads MSH, PID, PV1, ORC, OBR and DG1, as supplied. Only new orders (ORC-1 `NW`) are read. The placer group number (ORC-4) names the requisition, else the first ORC-2. It claims no profile conformance.
- **Accepting.** A message whose MSH-4 is not the connection's *Accept messages from* is refused. The ordering provider must be a registered, active practitioner by NPI (ORC-12, else OBR-16); PV1-3, if given, a location of the client; each OBR-4 an order code with an approved code mapping, which gives the LIS test and its sequence role (first line or confirmation) as the partner's contract defines it (REQ-INT-004). A diagnosis (DG1-3) is kept as supplied and refused without its coding system.
- **Patient.** The patient is found only by a PID-3 identifier, by assigning authority (else the sending facility) and type; the LIS never creates a patient from a message. With no match the message waits (or is refused, per *Unknown patient*) and becomes an order at the first reading after the patient is registered with that identifier. Two matching patients, or a registered patient whose family name or birth date differs, hold it for review.
- **Order.** The order is registered in Received status with source `HL7 interface (EMR)`, the placer number and authority, the stored message as its source document, and evidence as supplied: no signature evidence (the laboratory's order policy decides at acceptance, REQ-ORD-005), billing responsibility not supplied, no medications. The laboratory accepts or rejects it in Orders as any order.
- **Replays (REQ-INT-003).** An exact replay (the same bytes) is a duplicate with no effect. The same MSH-10 with other content is held for review. A placer number that already has an order is refused.
- **Logs.** Each message shows Dir. In, transport Received, and what it became: Order created, Waiting for patient, Held for review, Duplicate – ignored or Rejected with its reason, and where its file moved, or over MLLP the acknowledgement the EMR got and its address. The LIS writes no acknowledgement file back; for files, the clinic learns the outcome by the laboratory's agreed route.
- **Rejecting by hand.** A message waiting for its patient or held for review can be rejected from its row in Logs with **Reject…** and a reason (1–500 characters). No order is made from it, even if the patient is registered later, and the reason resolves it, so it does not stay under Rejected. The clinic is not told: over MLLP its EMR got AA when the message arrived, so the laboratory tells the clinic by its agreed route. The decision is audited (`interfaces.reject_received`).

## SFTP

The LIS connects out to the partner's SFTP server ([integrations](../architecture/integrations.md)); it never accepts connections. The client is russh with the ring backend, admitted in the [library policy](../governance/library-policy.md#sftp-client-admission--2026-11-04).

- **Server identity.** The connection pins the server's key by its SHA-256 fingerprint, as OpenSSH prints it (`SHA256:` and 43 characters). The LIS refuses any other key, and Test connection shows the fingerprint the server presented. Get the fingerprint from the partner's IT through a channel the laboratory trusts. The server must offer an Ed25519 or ECDSA host key; RSA is not supported (the `rsa` crate is excluded, RUSTSEC-2023-0071).
- **Sign-in.** SSH key (recommended): one Ed25519 key per installation, made on the first **Copy LIS public key**. Its private key is sealed with the installation key in the database and never leaves the engine; the partner's IT allows the public key (`ssh-ed25519 … vibetox-lis`) for the username. Password: sealed with the installation key, never returned to the screen, and kept on a change only while the server, port and username stay the same. Either needs the installation key on this computer; without it, attempts fail with `credential_unavailable`. A restore that brings the installation key brings both.
- **Writing.** Each file is uploaded under a temporary `.tmp` name in the remote folder and renamed when complete. An SFTP rename never replaces a file: a name taken by other content gets `-1`, `-2`; a name already holding the same bytes is taken as the earlier write of the same message. Connecting and each step without an answer time out after 20 seconds, then the usual retries apply.
- **Destination check.** It covers the server, port, username, remote folder and fingerprint together. Changing any of them needs a new check; changing the sign-in or the password does not.
- **Problems** in Logs and on Overview: `server_unreachable` (no answer, refused, or an RSA-only server), `fingerprint_mismatch`, `sign_in_failed`, `credential_unavailable`, and the folder codes `folder_missing`, `access_denied`, `name_taken`, `write_failed`.

## MLLP – LIS connects

An HL7 Results connection can send over MLLP: the LIS opens a TCP connection to the partner's interface, sends one message framed for MLLP (VT, the message, FS CR), reads the partner's application acknowledgement on the same connection and closes it ([integrations](../architecture/integrations.md)). Framing and acknowledgement reading are the LIS's own narrow code; no HL7 or MLLP library is bundled ([ADR 0007](../architecture/decisions/0007-integration-edge-and-interface-engines.md) §7).

- **Lab network only (REQ-INT-006).** MLLP is framing, not encryption. The partner's address must be an IP address on the lab network: private IPv4 (10/8, 172.16/12, 192.168/16), link-local, loopback, or IPv6 unique-local or link-local. Another address, or a server name, is refused when saving and again before every connection, so a changed record never sends patient data to the internet. A partner outside the lab network is reached through the laboratory's VPN, at the address the VPN gives it, or uses SFTP. MLLP over TLS is not available.
- **The message.** The ORU^R01 is the same as for a folder, except MSH-15 and MSH-16, which are empty over MLLP (original acknowledgement mode: the partner answers each message on the same connection) and `NE` for a file. No file name is used.
- **Acknowledgement.** The LIS waits up to the connection's ACK timeout (1–300 seconds, default 30) for an ACK whose MSA-2 names the message's control ID (MSH-10). MSA-1 `AA` shows as **Accepted (AA)**; `AE` as **Rejected (AE)** and `AR` as **Rejected (AR)**, with the partner's reason (ERR-8, else MSA-3, one line, at most 200 characters). A commit acknowledgement (`CA`), an unreadable answer or one for another message is not an acknowledgement. An acknowledgement is the partner's answer, never proof that a clinician saw the result.
- **No acknowledgement in time.** The message left, so it shows transport **Sent** and **Awaiting application ACK**, and is sent again at the usual retries (1, 2, 4 and 8 minutes), the same bytes with the same control ID, so the partner can recognize a resend. After the fifth attempt it fails and waits for **Send again**. Messages awaiting their acknowledgement are counted on Connections (**Waiting for acknowledgement**, column **Awaiting ACK**) and on the connection's Overview, not under Errors.
- **Rejected.** A message the partner answered with AE or AR is not sent again: it shows under **Logs › Rejected** with the partner's reason until a person resolves it with **Mark resolved…**. Correcting the result releases a new revision, which is sent as a correction.
- **Tests.** **Test connection** connects to the address and port and closes, sending nothing. **Send test message** sends the synthetic ORU^R01 (processing ID `T`) and shows the partner's answer.
- **Destination check.** It covers the partner's address and port. Changing either needs a new check; changing the ACK timeout does not.
- **Problems** in Logs and on Overview: `not_lab_network`, `partner_unreachable` (no answer or refused within 10 seconds), `connection_lost` (closed before the ACK), `no_ack`, `ack_unreadable`, `ack_other_message`.

## MLLP – LIS listens

An HL7 Orders connection can receive over MLLP: the LIS listens on an address of this computer on the lab network, the clinic's EMR interface connects and sends framed order messages, and the LIS answers each with an HL7 acknowledgement on the same connection ([integrations](../architecture/integrations.md)). This is the only inbound network listener for partners; the framing and the acknowledgement are the LIS's own narrow code ([ADR 0007](../architecture/decisions/0007-integration-edge-and-interface-engines.md) §7).

- **Lab network only (REQ-INT-006).** The listen address must be one of this computer's IP addresses on the lab network (the same ranges as for MLLP – LIS connects); an internet address and `0.0.0.0` (every address) are refused. Only the *Partner addresses allowed to connect* (1–20, each a lab-network address) are let in. A connection from another address is closed at once, without reading or answering; refusals are counted in memory and audited as `interfaces.reject_partner_connection` summaries on the security stream, at most once a minute per address (NFR-08). A partner outside the lab network connects through the laboratory's VPN, or uses SFTP. MLLP over TLS is not available.
- **Listening.** From engine start, whoever is signed in (also nobody), the LIS compares its listeners with the started HL7 Orders connections whose destination check covers their listener, every 5 seconds and at once after a connection is saved, started, stopped or checked. It starts each missing listener, stops one whose connection stopped, and restarts one whose settings changed. Nothing listens while a recovery reconciliation is open. A port another program holds, an address this computer does not have, or a port the system reserves (often below 1024) shows on the connection as **Not listening** with the reason and status **Error**; it is tried again every 5 seconds.
- **Limits per listener.** At most 4 partner connections at once (a fifth is closed); a message up to 1 MiB; bytes that are not MLLP frames, or a larger message, close the connection without an answer. A connection idle longer than *Idle timeout* (10–3600 seconds, default 300) is closed; the partner connects again.
- **Receiving.** Each message is stored, then recorded with what it became in one transaction with the order it makes, by the same rules as a file ([above](#hl7-orders-incoming)), with the partner's address. Only then is it answered. A message that could not be saved gets no answer and the connection closes, so the partner sends it again.
- **Acknowledgement.** Original acknowledgement mode: MSH addressed back to the sender (MSH-5/6 from its MSH-3/4), message type `ACK^<trigger>^ACK`, control ID `ACK-<its control ID>`, its processing ID, version 2.5.1; MSA-1 the code and MSA-2 the message's control ID. **AA** when the message is kept: an order made, waiting for its patient, or held for review. **AE** when its content is refused: an unknown test code, ordering provider or location, an unknown patient set to reject, a missing patient, order or test, or the order rules refusing it. **AR** when it comes from another sending facility, is not UTF-8 text or HL7, is not an OML^O21 or ORM^O01, has no control ID or is not a new order (ORC-1 `NW`). AE and AR carry the reason in words in MSA-3. An exact replay is answered with the code and reason the first one got and makes nothing. Enhanced mode (commit acknowledgements) is not supported; MSH-15/16 are ignored.
- **Tests.** **Test listener** opens the address and port for a moment and closes them; it passes when the connection's own listener already listens there. It contacts no partner. There is no test message: the EMR sends a synthetic order, which Logs show as Received with **ACK AA returned to <address>**.
- **Destination check.** It covers the listen address, the port and the allowed partner addresses. Changing any of them needs a new check, and the listener stops until it is recorded; changing a partner's note or the idle timeout does not, and restarts the listener with the new setting.
- **Problems** on Overview and Test listener: `port_in_use`, `address_not_on_this_computer`, `port_not_allowed`, `listener_failed`, `not_lab_network`.

## HL7 Results messages

The LIS's own narrow encoder writes the message (no HL7 library is bundled; [ADR 0007](../architecture/decisions/0007-integration-edge-and-interface-engines.md) §7). It claims no LRI conformance: the partner's contract and acceptance tests decide that, and the profile choices below are defaults to confirm with each partner.

| Segment | Content |
| --- | --- |
| MSH | Sending application `VIBETOX LIS`, the laboratory's name and CLIA number, the partner as receiving facility (MSH-6), the delivery ID as control ID (for the test message `TEST-` and a new ID each time), processing ID `P` (`T` for the test message), no acknowledgement requested in a file (`NE`; empty over MLLP, which answers each message), UTF-8 |
| PID, PV1 | The patient's identifiers (PID-3; the released revision's, else the patient's active identifiers when the message is made; never empty, see [held for an identifier](#how-messages-travel)), name and birth date as recorded, and the administrative sex as its HL7 table 0001 code in PID-8 (a recorded code or name, in any letter case: `F` Female, `M` Male, `A` Ambiguous, `N` Not applicable, `O` Other, `U` Unknown; any other recorded text is sent as `U`, and none recorded leaves PID-8 empty; the record is never changed); the client location (PV1-3), patient class `U` |
| ORC, OBR | One group per ordered test with a reported line: the ordering source's order number, a filler order number stable across revisions (report number and test position), the partner's test code (OBR-4), collection time, ordering provider by NPI, ordering facility (ORC-21), release time, status `F` or `C` for a correction |
| OBX | One per reported analyte: the partner's code and the LOINC code (the mapping's, else the catalog's), the value exactly as stored (NM), a censored value as comparator and number (SN), a qualitative code as received (ST), no value with status `X` when no result could be obtained; the mapping's UCUM unit, the reference interval if configured, the performing laboratory. No abnormal flag or interpretation is sent (REQ-RPT-008) |
| SPM | The accession number, the specimen type, collection and receipt times |

A withdrawal is sent as the withdrawn revision's results with OBX status `W` (posted in error) and OBR status `C`; confirm with each partner that its system removes them.

**Code mappings (REQ-INT-004).** Each HL7 connection maps LIS tests and analytes to the partner's codes, with LOINC and the UCUM unit. Changes are drafts on the connection's Code mappings tab; a second person approves them as a new version with a reason, or the person who drafted them where the separation-of-duties policy allows ([ADR 0015](../architecture/decisions/0015-separation-of-duties-policy.md)). The message is made at its first write attempt with the version then in force; its bytes and the version are kept, so every retry writes the same bytes and a later version never changes a written message. A message whose test or analyte has no approved mapping, or whose quantity's unit is not the mapping's unit, is held: never sent with a guessed code or a converted unit. The tab lists what held messages need.

## Set up a connection

Everything needs Manage configuration.

1. **Interfaces › Connections › Add connection.** Name the connection and its partner and choose the message (HL7 Results, Report PDF or Billing JSON). For HL7 Results, the partner's name is sent as the receiving facility (MSH-6).
   - **Folder:** **Choose folder…**: the folder comes from the system dialog and cannot be typed. **Test folder** writes and removes a probe file.
   - **SFTP:** enter the server, port, username, server fingerprint and remote folder. With SSH key sign-in, **Copy LIS public key** and send it to the partner's IT; with password sign-in, type the password. **Test connection** connects, checks the fingerprint and sign-in, and writes and removes a probe file. Nothing is saved by either.
   - **MLLP – LIS connects** (HL7 Results): enter the partner's address on the lab network, its port and the ACK timeout. **Test connection** connects and sends nothing.
   - **MLLP – LIS listens** (HL7 Orders): enter this computer's lab-network address, the port agreed with the EMR's IT, and the EMR interface's address, such as `192.168.1.50 (Hospital B interface engine)`. **Test listener** checks the port is free there. Allow the port through this computer's firewall for that address only.
2. Add **routing rules** when only some reports or handoffs belong to this partner. Choose the **schedule** and, except for MLLP, the **file name** (the message type's required placeholders and extension). **Save as stopped**.
3. On the connection's page, **Send test message** writes a synthetic file with no patient data: an ORU^R01 with processing ID `T` for HL7 Results, a one-page PDF for Report PDF, a JSON file for Billing JSON. Ask the partner to confirm it. For HL7 Results, add the partner's codes under **Code mappings** and have a second person approve them.
4. A second person uses **Record destination check** and records how the folder or server was confirmed. The laboratory's separation-of-duties policy decides whether the person who chose the folder may record it ([ADR 0015](../architecture/decisions/0015-separation-of-duties-policy.md)). The partner must be covered by a business associate agreement; that is the laboratory's responsibility.
5. On **Overview**, open **Interface contract**: **Draft v1** with the terms agreed with the partner's IT; a second person uses **Approve v1**; then **Run acceptance tests** until they pass ([below](#interface-contracts-and-acceptance-tests)).
6. **Start** the connection, with a reason.

Choosing another folder later, another SFTP server, port, username, remote folder or fingerprint, another MLLP partner address or port, or another listen address, port or allowed partner address, needs a new destination check before patient data goes there or is received.

## Interface contracts and acceptance tests

Each connection keeps a versioned interface contract and runs acceptance tests before patient data goes or comes (REQ-INT-001).

- **Contract.** A person drafts the terms agreed with the partner's IT: the message and profile (such as HL7 v2.5.1 ORU^R01, LRI Edition 5 based), what the partner's acknowledgements mean or how it confirms a file, how corrections and withdrawals are applied, what sits between the LIS and the partner (the LIS itself, or the laboratory's interface engine, named), who answers for it by role, and agreed deviations. A second person approves the draft as the next version with a reason, or the drafter where the separation-of-duties policy allows and they confirm it ([ADR 0015](../architecture/decisions/0015-separation-of-duties-policy.md)). Versions are append-only; History shows each approval, and the audit trail records drafts and approvals.
- **Acceptance tests.** **Run acceptance tests** runs the LIS's synthetic cases for the connection as it is now; nothing is sent. HL7 Results: the code mappings are approved with a UCUM unit for each analyte; synthetic ORU^R01 messages built with the partner and the approved mappings read back with the expected header, PID-3 filled, PID-8 as a table 0001 code, codes and unit, a censored value as SN with no abnormal flag, a correction with status `C` and a withdrawal with `W`; over MLLP, MSH-15/16 are empty. File connections: the file name pattern makes a valid name. HL7 Orders: synthetic OML^O21 messages go through the real receiving rules in one database transaction that is rolled back, after a synthetic patient and ordering provider are registered there: a mapped code makes an order, an exact replay makes no second order, the same message ID with changed content is held, an unknown test code and another sending facility are refused, an unknown patient waits or is refused as set; over MLLP each gets its expected AA, AE or AR. Nothing the order cases make is kept or audited; the run itself is recorded and audited (`interfaces.run_acceptance_tests`).
- **Gate.** Patient data goes or comes only once a contract version is approved and the latest run for the connection's current acceptance key passed. The key names the contract version, the code mapping version and the settings that shape the messages (partner, message type, protocol, file name pattern, what is accepted, how it is acknowledged); the destination and schedule are not part of it, as the destination check covers the destination. A new contract or mapping version, or a change to those settings, makes the tests **out of date**: deliveries wait with **Interface contract not approved, or its acceptance tests not passed**, files are not read, and a listener stops, until the tests pass again. A run is refused if the connection changed while it ran.
- **What it proves.** The tests check the LIS's side of the boundary on synthetic data. They do not prove that the partner processes the messages correctly, and claim no profile conformance; the partner's acceptance is qualified with the partner and recorded in the contract's terms.

## How messages travel

- **Routing.** Releasing a report revision makes one message of each report type (HL7 Results, Report PDF), and creating a handoff one Billing JSON message, in the same transaction, when at least one connection of the type exists. An HL7 rule names its field by the HL7 field that carries it (ORC-21, OBR-16, PV1-3, OBR-4) but compares the LIS codes. It goes to every connection whose rules all match. A rule matches only if every value of its field meets it, so a handoff covering two clients never goes to one client's partner alone. A report's values are its order's client, practitioner and location and the tests on its specimen. With no rules, a connection receives every message of its type. Without any connection of the type no message is made, and files are exported by hand as before.
- **Corrections and withdrawals (REQ-RPT-013).** A report's later revision, correction or supplement, goes first to every connection of the same type that had an earlier revision (HL7 with corrected status `C`), even when its rules no longer match, and is written before other waiting messages. An earlier revision not written yet is superseded: it is never written, and an unrouted one leaves Unrouted messages. A withdrawal notice or HL7 withdrawal goes to every connection an earlier revision was written to; with none, no message is made.
- **Impact pause (L13).** A report revision waits, unwritten, while its impact review is open or a correction is due; Logs say so. Withdrawal notices never wait for it.
- **Held for a patient identifier.** HL7 v2.5.1 requires PID-3. When neither the released revision nor the patient's record has an active identifier, the HL7 message is not written or sent: Logs show **Held: the patient has no identifier; add one on the patient's page**, and every pass looks again. The release itself is never blocked or delayed by this. Add the identifier on the patient's page (Patients › the patient › Add identifier); the message is then made with the patient's active identifiers, the released content unchanged. Adding an identifier changes the patient's record after release, so the report's impact review opens first (L13): on the report, **Record impact assessment** with **No impact on the released report** (or a correction, which then goes instead), and the message goes at the next pass. Report PDF and billing messages are not affected.
- **Writing.** While the app is open, at the sign-in screen too, the LIS looks every 10 seconds for messages it may write. A message is written only while its connection is started, a destination check covers its current folder or server, its interface contract is approved and the latest acceptance tests for it as it is now passed, its schedule allows it, and no recovery reconciliation after a restore is open. The file is the stored file, byte for byte: the issued report PDF is never regenerated. It is written under a temporary `.tmp` name, synced (in a folder), and only then given its final name. An existing file is never replaced: a name taken by other content gets `-1`, `-2` before the extension.
- **Retries.** A failed write is retried after 1, 2, 4 and 8 minutes. After the fifth failure the message waits for **Send again** in **Logs › Failed** and appears in the **Interface messages not written** work queue. Sending again uses the same stored file and never makes a new message or report.
- **Evidence.** Logs show what the folder, server or MLLP connection can prove: **Written** (**Uploaded** for SFTP, **Sent** for MLLP), **Failed** or **Not sent**. A folder or SFTP server never confirms that the other system used the file, so a written file shows **Outcome unknown**, never Delivered; an MLLP partner's acknowledgement shows as **Accepted (AA)**, **Rejected (AE/AR)** or **Awaiting application ACK**. The billing owner's acknowledgement or rejection is recorded on the handoff (REQ-BIL-002). A written report PDF is not a staff-attested delivery on the report's page, but a revision that goes to a connection leaves the **Reports without a destination** work queue. Each write attempt is an audit event on the security stream; routing, connection changes, destination checks, unrouted decisions and log exports are audited too.
- **Resolving rejections.** A message the partner rejected (AE, AR) or the LIS refused stays under **Logs › Rejected** until a person resolves it with **Mark resolved…** and a note on what was done (1–500 characters), such as the clinic sending the order again. It then leaves Rejected and stays under All, its Details naming who resolved it, when and the note. A rejection is resolved once; the decision is audited (`interfaces.resolve_rejection`). Resolving changes nothing at the partner and sends nothing.

## Unrouted messages

A message that matched no connection waits in **Interfaces › Unrouted messages** and in the **Unrouted interface messages** work queue; the menu shows the count. Its panel shows the connections it was checked against and the closest rule. Choose one decision:

| Decision | Effect |
| --- | --- |
| Send once | One delivery to the chosen connection, under its usual checks |
| Retry routing | Routes it by the rules as they are now; refused while no rule matches |
| Deliver another way | Records how it was delivered outside the LIS, for reconciliation |
| Dismiss with reason | Leaves it undelivered, with the reason |

**Add a rule** opens the closest connection, where Edit changes its rules.

## Recovery

| Symptom | Action |
| --- | --- |
| Connection shows **Error** | Overview names the latest problem. Restore the folder, the server or the permissions, use **Test connection**, then **Send again** on failed messages |
| An HL7 Orders connection shows **Error** | Overview's **Last connection** names the reading problem, such as Folder not found. Restore the folder, the server, the sign-in or the permissions; the connection is Active again after the next reading that works, and files not read are read then |
| A rejection stays under **Rejected** | Act on its reason with the partner or the clinic, then use **Mark resolved…** on its row with what was done |
| An order message should not become an order | While it waits for its patient or is held, use **Reject…** on its row with the reason, and tell the clinic |
| SFTP **fingerprint mismatch** | Do not copy the presented fingerprint. Confirm with the partner's IT through a trusted channel whether the server's key changed; if it did, Edit the fingerprint and record a new destination check |
| SFTP **sign-in failed** | Check that the partner allowed the LIS public key for the username, or type the password again |
| SFTP **credential unavailable** | Use Copy LIS public key once to make the LIS key, type the password again, or restore the installation key (System › Recovery kit shows whether it is usable) |
| MLLP **partner unreachable** | Check the address and port with the partner's IT, that its interface runs, and that the lab network or VPN lets this computer connect out to that port; then **Test connection** |
| MLLP messages stay **Awaiting application ACK** | The partner's interface takes the message but does not answer with an application ACK in time. Ask the partner's IT to check its acknowledgement mode, or raise the ACK timeout; the LIS resends the same message until the fifth attempt |
| MLLP **Rejected (AE/AR)** | Read the partner's reason in Details; fix the cause with the partner (a mapping, a provider, the partner's own setup). A corrected result goes as a correction |
| MLLP listener **Not listening** | Overview gives the reason. Free the port or choose another, or use this computer's current lab-network address, then **Test listener**; the LIS tries again every 5 seconds. A new address or port needs a new destination check and the EMR's IT to send there |
| The EMR gets **no answer** or a closed connection | Check the connection is started, verified and **Listening**, and that the EMR connects from an allowed address: refusals appear in the audit trail as `interfaces.reject_partner_connection`, not in Logs. A message over 1 MiB or not framed as MLLP closes the connection; a message the LIS could not save gets no answer and is sent again |
| An order received over MLLP was answered **AE or AR** | Logs give the reason. Fix the mapping, provider or settings, then ask the clinic to send it as a new message: an exact resend is a replay and gets the same answer |
| Messages stay **Not sent** | The row's details say why: connection stopped, destination check not recorded, waiting for the schedule, paused for the report's impact review, held for a code mapping, held for a patient identifier, or written at the next pass |
| An HL7 message is **held: the patient has no identifier** | Add the identifier (with its assigning authority and type, as agreed with the partner) on the patient's page, then on the report use **Record impact assessment** with **No impact on the released report**; the message goes at the next pass |
| An HL7 message is **held** for a code mapping | Map the rows marked Not mapped – held on the connection's Code mappings tab, with the result's unit as the UCUM unit, and have a second person approve them |
| A report revision shows **Replaced by a newer revision** | Nothing to do: the newer revision went to the connection instead |
| The app was closed | Nothing is written, read or received while it is closed. Waiting messages are written after it starts again; an MLLP partner sends again what was not acknowledged |
| A restore was applied | Writing is held until the recovery reconciliation closes |
| Messages wait with **Interface contract not approved, or its acceptance tests not passed** | Open **Interface contract** on Overview. Approve a version if none is in force, then **Run acceptance tests**; a failed case names what to fix, such as an analyte mapping without a UCUM unit. After a mapping or contract change the tests are out of date until they run again |

## Limits

- Connections are stopped, not deleted, so their history and messages remain.
- An outgoing message opens in a side panel in Logs (`get_partner_message`, ticket #4678): its control ID (MSH-10), the partner's answer, its attempts from the audit trail and, for HL7 Results, the message as sent. That is the copy kept when the message was made (`payload_sha256`; for a test message, the message's stored file), read back and verified against its digest; every attempt sent those bytes. It is never made again: a message made later from the same revision could differ (code mappings, catalog LOINC codes, the connection's partner, the HL7 builder). Missing or damaged bytes are not shown. Each opening is an audited `access` read (`interfaces.get_message`). The Logs search also finds a message by its whole control ID. Report PDFs are opened from Reports, and the handoff file from Billing › Billing handoffs, by people with those rights, as audited reads; a received order's content is not shown.
- The folder's network share, permissions and the partner's process for reading files are the laboratory's to qualify. Passing tests on synthetic data is not qualification.
- The SFTP transport is tested against an in-process server on synthetic files, not against a partner's server. Each partner's server, network path and account are the laboratory's to qualify.
- The MLLP transport is tested against an in-process partner on localhost with synthetic messages. Each partner's interface, its acknowledgement behavior, the network path or VPN, and what AA, AE and AR mean for it are the laboratory's to qualify in the partner's contract.
- The MLLP listener is tested with an in-process EMR client on localhost and synthetic orders. The EMR's resend behavior after no answer or a closed connection, this computer's firewall and its lab-network address are the laboratory's to qualify. While the app is closed, as when an update installs, nothing listens.

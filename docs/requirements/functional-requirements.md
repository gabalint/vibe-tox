# Functional requirements

Status: current requirements baseline, maintained during implementation. The [implementation plan](../planning/implementation-plan.md#status) and [current quality gates](../quality/README.md) record implementation status and remaining acceptance limits. The [product scope](../project-scope.md#product-decision) and [ADR 0009](../architecture/decisions/0009-single-computer-local-lis.md) define the local application; optional hosted services remain proposals ([ADR 0010](../architecture/decisions/0010-optional-cloud-services.md)). Each laboratory runs its own installation, with its sites and client organizations as authorized scopes. The first clinical pilot must have a bounded, laboratory-approved menu and validated operating procedures. A synthetic demo does not satisfy any clinical acceptance criterion.

Terms: the **laboratory** is the legal lab entity that runs its own installation (the HIPAA covered entity). A **service provider** is an entity that would host optional **cloud services** for laboratories, with business-associate obligations where those services handle laboratory PHI. The **host computer** is the single lab PC that runs the LIS; a **LAN workstation** is an optional extra seat (Q-28). The **application** is the open-source local LIS on the host computer.

Priority: **P0** is required for the first operational pilot when the function is applicable; **P1** completes the broader clinical LIS product; **P2** is a separately scoped extension. **P0 (conditional)** applies only when the stated condition holds, usually that the partner selects the cloud service in question for the pilot. P0 does not authorize patient use or imply all interfaces must be built immediately. A P0 requirement can be met by a documented controlled handoff where explicitly stated. Acceptance statements describe observable behavior to verify; synthetic implementation tests do not replace laboratory validation.

Traceability: [WF-01–WF-20 and INV-01–INV-16](workflows.md); [domain concepts](../architecture/domain-model.md); [integration boundaries](../architecture/integrations.md). These are project-derived requirements informed by [laboratory research](../research/laboratory-practices.md), [external-service scope and evidence](../research/cloud-services.md), [single-PC technology research](../research/single-pc-technology.md) and [desktop application stack research](../research/desktop-application-stack.md) (ENG-130–136, ENG-144, ENG-146); regulatory obligations require the separate applicability analysis ([regulatory landscape §15](../research/regulatory-landscape.md#15-single-pc-distribution-and-optional-hosted-services)). DOM, SR and ENG IDs resolve in the [source ledgers](../research/README.md); REG IDs in the [compliance matrix](compliance-matrix.md); NFR IDs in the [nonfunctional requirements](nonfunctional-requirements.md); Q IDs in [open questions](../planning/open-questions.md). Requirements that reference payer behavior make it configurable policy supplied by the laboratory's billing/compliance owner; none decides medical necessity or embeds cutoffs, drug-class lists or interpretation rules.

## Cloud services

These requirements cover proposed optional external services for participating laboratories ([ADR 0010](../architecture/decisions/0010-optional-cloud-services.md), proposed). The cloud relays, stores and delivers copies; it never runs laboratory workflows or changes clinical state (INV-14). Each service has a local equivalent in the application (INV-16). Unless stated otherwise, each is **P0 (conditional)**: P0 when the partner selects a cloud service for the pilot. Service agreements, business-associate scope and referral-related boundaries require counsel review; these proposals are not legal conclusions.

## Pilot definition and pending decisions

The first pilot is a **single-computer installation** at one design-partner laboratory. It runs the desktop application on one Windows, macOS or Linux host computer that meets the Q-29 baseline, with per-person local accounts (REQ-IDN-004), a signed installer and lab-approved updates (REQ-OPS-006), local encrypted backup and a rehearsed restore to a replacement computer (REQ-OPS-007), host health checks (REQ-OPS-008), offline operation (REQ-OPS-009), open-application operation (REQ-OPS-013), complete exit export (REQ-OPS-010) and at least one analyzer driver (REQ-INT-009). LAN workstations (REQ-OPS-011) are P1 and enter the pilot only if Q-28 is decided that way.

The pilot also includes P0 identity, specimen, method/QC, result/review, reporting/correction with per-channel delivery evidence (REQ-RPT-011–REQ-RPT-013), traceable referral handling, minimal quality links, billing handoff, downtime and audit behavior. For proposed outpatient drug monitoring it also includes per-patient order evidence, standing-order/profile guards and medication context (REQ-ORD-005/006/007), validity report consequences (REQ-SPC-008), controlled menu extension and upstream-review import semantics (REQ-ANA-009, REQ-ANA-003), drug-monitoring report content, remote-review location and patient access/EHI export (REQ-RPT-008/001/009), class-based service derivation and claim-review packages (REQ-BIL-005/006), and the Medicare documentation retention class (REQ-OPS-003). Payer rules are configurable inputs owned under Q-21; the LIS never decides medical necessity.

**Cloud services in the pilot.** A cloud service is in pilot scope only if the partner selects it; then the matching conditional requirements become P0 and the service runs under a BAA. The client portal (REQ-ORD-008–REQ-ORD-011, REQ-RPT-014) is proposed and it is not a precondition for clinical correctness: every P0 clinical workflow must pass its acceptance with no cloud service enabled, using the application's manual entry, printing and delivery routes.

Conditional priorities: REQ-RES-007 is P0 only when Q-22 confirms the laboratory offers medication-consistency reporting and stays disabled otherwise; REQ-RPT-010 is P0 only when a patient- or client-facing digital channel is in pilot scope; REQ-INT-007 is P1 but becomes P0 when the pilot menu and states include reportable analytes. REQ-QMS-006 is P1 because a single-certificate pilot can control certificate scope manually. Cloud-service conditions are stated in each row; REQ-SVC-003's telemetry clause applies to every install.

**Current count: 102 functional requirements (79 P0, of which 14 are conditional on a cloud service and 2 on other conditions; 20 P1; 3 P2).** The [validation plan](../quality/validation-plan.md#requirement-coverage) maps every P0 requirement to planned scenarios; the single-computer and cloud-service requirements map to VAL-37–VAL-57 ([coverage](../quality/validation-plan.md#coverage-of-reg-044reg-050-nfr-23nfr-32-and-the-single-computer-requirements)). That mapping is an index of planned evidence, not executed validation.

P1 and P2 priorities are planning defaults, not a claim that a laboratory may omit an applicable obligation. For example, a laboratory may already use an external QMS or billing system, while a pilot offering federal workplace testing would need program requirements promoted to P0 and independently validated. No source supports treating this requirements list as laboratory certification.

Patient-access request handling and applicable PT routing safeguards are pilot obligations under REG-015/016/028 even if a self-service portal or full PT management module remains P1. A controlled manual process or qualified external system may cover those obligations only with assigned ownership, deadlines, evidence and validated handoffs.

**Authentication limits (REQ-IDN-004, NFR-19).** Role-wide FIDO2 enforcement for release and administration and the sealed break-glass account are not yet established. Implementation status is in the [implementation plan](../planning/implementation-plan.md#status); hardware/OS qualification and production policy remain [G2-09](../quality/open-items-g1-g2.md).

**Laboratory touch-only policy acceptance (REQ-IDN-004; [ADR 0019](../architecture/decisions/0019-security-key-authentication.md)).** The default refuses presence-only credentials. An explicit laboratory opt-in permits them only for subsequent own-account enrollment, sign-in and same-user key unlock. Acceptance covers fresh confirmation for policy changes, a reason when enabling the option, ending other laboratory sessions and invalidating pending proofs; preservation of existing credential verification requirements; no fallback after a failed PIN; refusal of unverified first signup, replacement-key recovery and sensitive-action proofs; and rejection when the policy changes during a ceremony. Touch-only is single-factor authentication and requires laboratory acceptance of the physical-access risk; it does not close G2-09.

**Personal session-unlock PIN acceptance (REQ-IDN-004, NFR-19; [ADR 0019](../architecture/decisions/0019-security-key-authentication.md)).** An optional six-digit PIN resumes only the same person's locked, unexpired session. Acceptance scenarios cover off-by-default configuration with fresh normal authentication, encrypted verifier/user-purpose binding, five consecutive failures ending the session, no counter reset from reopening the prompt, reset on successful PIN verification, no initial/restart/user-switch/expired-session bypass, no extension of the 12-hour absolute lifetime, normal fresh confirmation for sensitive actions, PIN removal on administrative reset/key recovery, audit attribution and cancellation of queued unlocks after lock/sign-out/expiry. These local convenience controls do not establish MFA, NIST assurance conformance or closure of the existing hardware/production-policy gates.

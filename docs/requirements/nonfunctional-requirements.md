# Nonfunctional requirements

Status: proposed targets requiring workload and platform qualification. Product, laboratory and operations owners must accept the workload and service objectives before capacity purchasing or a pilot commitment. Targets for optional external services are separate and outside the current implementation scope ([ADR 0010](../architecture/decisions/0010-optional-cloud-services.md)). [Deployment](../architecture/deployment.md), [single-computer technology research](../research/single-pc-technology.md) and [desktop stack research](../research/desktop-application-stack.md) describe the environments and supporting evidence. Acceptance scenarios run on synthetic data in development and do not replace laboratory validation.

## Planning workload

The accepted target is **100–250 patients per day**. Patients are not interchangeable with accessions, specimens, executions or observations.

| Parameter | Current target or benchmark assumption | Qualification |
| --- | --- | --- |
| Patients | 100–250 per day | Project-owner target; actual visit patterns remain Q-10 |
| Accessions and specimens | State each count separately, including multiple specimens per patient | No assumed universal ratio |
| Executions and observations | Include multi-analyte specimens, repeats/re-extractions/dilutions and QC separately | Benchmark assumptions do not approve assay menus |
| Historical records | Accumulated records plus queues exceeding page limits | A single-day fixture cannot establish capacity |
| Import bursts | Peak batch imports alongside interactive reads and reconciliation | Report batch size, retained input size and timing |
| Interactive users | Current scope is one local desktop; additional LAN workstations remain Q-28 | Concurrent-user workload needs separate qualification |
| Writers | One serialized writer on the laboratory computer | No new service or database infrastructure prescribed without measurement |

Capacity must be qualified using the [validation plan](../quality/validation-plan.md) and the [open host/performance gates](../quality/open-items-g1-g2.md). Development-host measurements do not qualify every supported OS, production hardware, retention duration or laboratory workflow. Technology estimates of SQLite headroom remain hypotheses. Operating days, turnaround and recovery commitments remain Q-10.

Raw mass-spectrometry files may dominate storage. Estimate each class separately as count × average bytes × retained duration × copies, including growth, indexes, messages, reports, backups and audit. Do not infer raw-data capacity from result-row counts. On one computer, storage growth also sets snapshot duration and backup size, so measure both. Benchmark with realistic synthetic batch sizes, skew, history, roles and failure cases.

The accessibility target follows [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) as a design standard, without asserting blanket legal applicability. All numeric performance and recovery values above are project proposals. Stronger requirements may follow from actual turnaround obligations, staffing, geography, analyzer throughput and downtime tolerance. NFR-34–NFR-35 are reserved.

## Measurement details to settle

Define monitoring interval, operating hours, maintenance window, partial-degradation rules and dependency coverage before accepting the NFR-28 cloud objectives. Define the recovery incident start/end, achievable snapshot and off-PC copy cadence, hardware-replacement assumptions and acknowledged-data-loss semantics before accepting NFR-04 and NFR-30. A database restore alone is not proof that finalized report artifacts, locally spooled instrument results or cloud-held receipts are recoverable. Provide enough load and storage evidence to revise these targets before production, rather than advertising an untested service level.

NFR-19–22 adopt items from the **proposed** HIPAA Security Rule NPRM and the **voluntary** HHS Cybersecurity Performance Goals as design targets, not as current legal mandates. NFR-17 depends on the REG-016 applicability decision and the privacy-approved designated-record-set inventory. Its export-time target is a planning value. [ENG-35–42](../research/sources-engineering.md)

The local-computer and optional-service proposals are supported by [technology research](../research/single-pc-technology.md) and the [regulatory landscape](../research/regulatory-landscape.md#15-single-pc-distribution-and-optional-hosted-services). The accepted desktop scope is defined by [ADR 0009](../architecture/decisions/0009-single-computer-local-lis.md) and [ADR 0012](../architecture/decisions/0012-rust-tauri-desktop-application.md).

NFR-01 and NFR-02 describe correctness goals for normal processing and recovery; they do not assert zero physical data loss under every disaster. NFR-04 must identify the recoverable evidence and residual loss window for each class, while the downtime procedure identifies affected work and prevents silent resumption. Current-authorization checks in NFR-08 apply even when a historical report was legitimately issued to the same recipient. Exact report bytes and history remain retained with restricted access.

Acceptance scenarios for the [ADR 0019](../architecture/decisions/0019-security-key-authentication.md) laboratory touch-only option and personal session-unlock PIN, and the current limits against REQ-IDN-004 and NFR-19, are recorded with the [functional requirements](functional-requirements.md#pilot-definition-and-pending-decisions).
